INTERFERENCE RISKS — WHY ORDER MATTERS:
-----------------------------------------
Feature 4 (Prometheus Alert Demo) requires temporarily scaling course-service
to 0 replicas. While it is down:
  - Grafana's "Services Up" panel drops from 4 to 3  (shows RED)
  - The ServiceDown alert fires and remains active for up to 5 minutes
  - If you show Grafana AFTER this without waiting, it will look broken

Feature 5 (ArgoCD Self-Heal) scales ml-service to 0 temporarily. While it
is scaling down and being restored (~60 seconds):
  - The ML prediction endpoints in the app will return errors
  - MLflow UI is NOT affected (it is a separate pod)

SAFE DEMO ORDER (strictly follow this):
  1. SonarQube          — read-only, no state changes
  2. MLflow             — read-only, no state changes
  3. Grafana            — read-only, show everything green
  4. Prometheus Alerts  — triggers ServiceDown alert (course-service down ~2 min)
  5. ArgoCD Self-Heal   — last, ml-service briefly down ~60 seconds

NEVER swap steps 3 and 4. You cannot show a healthy Grafana dashboard after
triggering the alert unless you wait 5 full minutes for it to clear.

================================================================================
  FEATURE 4: PROMETHEUS ALERTING — LIVE ALERT DEMO
================================================================================

WHAT THIS DEMONSTRATES:
  Four custom Prometheus alert rules monitor YBrainy services. AlertManager
  routes alerts by severity. When a service goes down, an alert fires within
  60 seconds. When it recovers, the alert automatically resolves.

TALKING POINTS:
  - 4 alert rules: ServiceDown (critical), HighMemoryUsage (warning),
    HighErrorRate (warning), SlowResponseTime (warning)
  - AlertManager has severity-based routing: critical alerts go to a separate
    receiver, inhibit rules prevent warning spam during critical incidents
  - Alert rules are deployed as Kubernetes ConfigMaps (version-controlled)

  !!!! WARNING: DO NOT SKIP THE RESTORE STEP !!!!
  If you forget to scale course-service back to 1 replica, all demos that
  depend on course-service will fail. Set a phone timer for 3 minutes.

STEP 1 — Show the alert rules (BEFORE triggering anything)
  1a. Open: http://172.22.108.68:30090/#/alerts
  1b. You will see the 4 alert rules, all showing "0 active" with State=inactive
  1c. Explain each rule:
      - ServiceDown: fires when any of course/lesson/quiz/enrollment is down
        for > 1 minute
      - HighMemoryUsage: fires when JVM heap > 85% for 2 minutes
      - HighErrorRate: fires when HTTP 5xx rate > 0.1 errors/second (5-min window)
      - SlowResponseTime: fires when p95 response latency > 2 seconds for 3 minutes

STEP 2 — Show AlertManager configuration
  2a. Open: http://172.22.108.68:30093
  2b. Show the Alerts page (currently empty — no active alerts)
  2c. Click "Status" → "Config" to show the alertmanager.yml configuration

STEP 4 — Watch the alert progress (takes ~60 seconds)

  4b. After ~15 seconds: Prometheus detects up=0 for course-service

  FEATURE 5: ARGOCD GITOPS + SELF-HEALING (DO THIS LAST)
================================================================================

WHAT THIS DEMONSTRATES:
  GitOps continuous delivery with automatic self-healing. The ml-service
  Kubernetes manifests are tracked in a local git repository. ArgoCD detects
  any drift between the desired state (in git) and the live cluster state.
  With selfHeal=true, ArgoCD automatically restores the correct state without
  human intervention.

TALKING POINTS:
  - GitOps principle: git is the single source of truth for infrastructure
  - ArgoCD continuously reconciles the cluster against the git repository
  - selfHeal=true means unauthorized kubectl changes are automatically reverted
  - The git source is a local bare repository served via git daemon on port 9418
    (workaround for monorepo size — full GitHub fetch times out)
  - This is a production-grade pattern used by teams to prevent configuration
    drift in Kubernetes clusters

  1g. Click "Details" to show:
        Source: git://172.22.108.68:9418/ml-k8s.git

        Sync Policy: automated, selfHeal=true

  In terminal confirm:

================================================================================
  TROUBLESHOOTING — IF SOMETHING GOES WRONG DURING THE DEMO
================================================================================

PROBLEM: ArgoCD shows "Unknown" status after startup
SOLUTION:
  wsl -e bash -c "pgrep -a git | grep daemon"  (check git daemon)
  If not running:
    wsl -e bash -c "git daemon --base-path=/tmp --export-all --port=9418 --reuseaddr --detach"
    wsl -e bash -c "kubectl annotate app ml-service -n argocd argocd.argoproj.io/refresh=hard --overwrite"
  Wait 30 seconds then refresh.

PROBLEM: kubectl commands fail with "connection refused" or "no server found"
SOLUTION: K8s cluster is not running — run the cgroup fix:
  wsl -e bash -c "sudo bash /mnt/c/Users/azizs/Downloads/ESPRIT-PI-4SAE4-2025-2026-Ybrainy/DEVOPS/fix-containerd-cgroup.sh"
  Wait 60 seconds then retry.

PROBLEM: MLflow shows no models
SOLUTION: Check MLflow pod:
  wsl -e bash -c "kubectl get pods -n ybrainy | grep mlflow"
  If CrashLoopBackOff: wsl -e bash -c "kubectl delete pod -l app=mlflow -n ybrainy"
  If pod recreates and models are gone: PVC may have been deleted. Trigger
  ml-service-CI pipeline in Jenkins to re-register models.

PROBLEM: course-service is still down after the alert demo
SOLUTION: Restore immediately:
  wsl -e bash -c "kubectl scale deployment course-service -n ybrainy --replicas=1"
  Then verify: wsl -e bash -c "kubectl get pods -n ybrainy | grep course"

PROBLEM: Alert is still firing 10+ minutes after restoring course-service
SOLUTION: This means Prometheus has not evaluated recovery yet. Wait. Or:
  Check the service is actually up:
  wsl -e bash -c "kubectl get pods -n ybrainy | grep course"
  If not Running: fix the pod first, then wait for alert to clear.

PROBLEM: ArgoCD app stays in OutOfSync after self-heal demo
SOLUTION: Manually trigger sync:
  wsl -e bash -c "kubectl annotate app ml-service -n argocd argocd.argoproj.io/refresh=hard --overwrite"
  Wait 30 seconds. If still OutOfSync, do a manual sync:
  wsl -e bash -c "kubectl patch app ml-service -n argocd -p '{\"operation\":{\"sync\":{}}}' --type=merge"

PROBLEM: SonarQube shows no "frontend" project
SOLUTION: The frontend-CI build must complete the SonarQube Analysis stage.
  Go to Jenkins http://172.22.108.68:8086 → frontend-CI → trigger a new build.
  Wait for SonarQube Analysis stage to complete (green checkmark).
  Then check http://localhost:9000 again.

PROBLEM: Grafana shows no data in panels
SOLUTION: Prometheus might not be scraping. Check:
  http://172.22.108.68:30090/targets
  All targets should be State=UP. If any are DOWN, the pod might be crashing —
  restart it:
  wsl -e bash -c "kubectl delete pod -l app=<service-name> -n ybrainy"
